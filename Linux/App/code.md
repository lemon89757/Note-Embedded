## 关于 `mmap` 函数
1. 在 `copy_mmap.c` 文件中，直接通过将文件描述符 `fd_old` 映射到内存空间进行对应文件数据的拷贝：
```C
...
if(fstat(fd_old, &stat) == -1){
    printf("can not get status of file %s.\n", argv[1]);
    return -1;
}

buf = mmap(NULL, stat.st_size, PROT_READ, MAP_SHARED, fd_old, 0);   // stat.st_size: size of file, in bytes.
if(buf = MAP_FAILED){
    printf("can not mmap file %s.\n", argv[1]);
    return -1;
}
...

if(write(fd_new, buf, stat.st_size) != stat.st_size){
    ...
}
```
2. 在 `showpixel.c` 和 `show_ascii.c` 中，通过将 frame buffer 映射到内存中，对 lcd 进行操作：
```C
...
fd_fb = open("dev/fb0", O_RDWR);
if(fd_fb < 0){
    ...
}
if(ioctl(fd_fb, FBIOGET_VSCREENINFO, &var)){
    ...
}
...
fb_base = (unsigned char *)mmap(NULL, screen_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd_fb, 0);
if(fb_base == MAP_FAILED){
    ...
}
// 清屏
memset(fb_base, 0xff, screen_size);      // 在这里为什么在操作完这块内存后显示就能更新，明明它还没有对相关设备进行写操作
...
```
- 帧缓冲设备的**物理内存通过 `mmap` 被映射到用户空间**后，任何对映射内存的写操作都会直接写入物理内存；
- 显示硬件（如 LCD 控制器）会**定期读取帧缓冲设备的物理内存**，并将其内容显示在屏幕上；
因此，当程序通过 `memset` 修改映射内存时，这些改动会立即反应到屏幕上。

## 关于 `select, poll, epoll`
1. 在 Linux 系统中实现 IO 复用的几种方式以及它们之间的关系：
- **select**
    - 它是一种早期的 IO 复用机制。它通过一个函数调用，传入一组文件描述符集合（可以理解为一个包含多个文件描述符的数组），然后让进程进入阻塞状态，等待这些文件描述符中的任何一个变为可读、可写或者有异常事件发生。
    - 例如，一个服务器进程可能同时监听多个客户端的连接，它会将这些连接对应的文件描述符都传给 select 函数。当有客户端发送数据（文件描述符可读）或者可以向客户端发送数据（文件描述符可写）时，select 函数就会返回，告知进程哪些文件描述符发生了事件，然后进程就可以对这些文件描述符进行相应的读写操作。
    - 但是 select 有一些限制，比如它有一个最大文件描述符数量的限制，通常是 1024，这在处理大量连接时会比较受限。
- **poll**
    - poll 也是实现 IO 复用的一种方式。它和 select 类似，也是通过一个函数调用，传入一个包含多个文件描述符信息的数组，然后等待这些文件描述符的事件发生。
    - poll 相比 select，没有最大文件描述符数量的限制，理论上可以处理更多的连接。不过它也有缺点，比如当文件描述符数量非常多时，每次调用 poll 函数都需要遍历整个文件描述符数组来检查事件，效率会比较低。
- **epoll**
    - epoll 是 Linux 系统下提供的一种更为高效的 IO 复用机制。
    - 它通过一系列的系统调用来实现对多个文件描述符的监控。首先，epoll_create 函数创建一个 epoll 实例，然后使用 epoll_ctl 函数将需要监控的文件描述符添加到这个实例中，并且可以为每个文件描述符设置关注的事件（如可读、可写等）。当有事件发生时，epoll_wait 函数会返回发生事件的文件描述符集合。
    - 与 select 和 poll 不同，epoll 不需要在每次调用时都传递和检查大量的文件描述符信息，它在内部维护了一个数据结构（通常是红黑树等高效的数据结构），能够高效地管理文件描述符和事件，因此在处理大量并发连接时性能更好。

2. 关于 `epoll` 改进了前两者，更加高效、性能更好：
- **效率方面**
    - 在 select 和 poll 中，当监控的文件描述符数量很多时，每次调用 select 或 poll 函数都需要遍历所有文件描述符来检查事件，这个过程的时间复杂度是 O(n)，其中 n 是文件描述符的数量。而 epoll 内部使用高效的数据结构来管理文件描述符和事件，当有事件发生时，它能够快速地找到发生事件的文件描述符，不需要每次都遍历所有文件描述符，所以效率更高。
- **性能方面**
    - 在高并发场景下，epoll 能够更好地利用系统资源。比如，它减少了系统调用的次数（相比 select 和 poll），因为不需要频繁地将文件描述符集合传递给内核进行检查。而且，epoll 的事件通知机制更加灵活，可以采用边缘触发（只在状态发生变化时通知）或水平触发（只要满足条件就一直通知）等方式，可以根据不同的应用场景选择合适的触发方式，从而提高性能。
    - 例如，在一个高并发的 web 服务器中，使用 epoll 可以同时处理大量的客户端连接请求，及时响应客户端的读写事件，而不会像 select 和 poll 那样在大量连接时出现性能瓶颈，导致响应延迟增加。

3. 为什么相比之下，`epoll` 的效率更高：
`epoll` 的效率更高，主要得益于其在设计和实现上对文件描述符管理和事件通知机制的优化。相比之下，`select` 和 `poll` 在处理大量并发连接时会暴露出明显的效率问题。以下是具体原因：

3.1 **文件描述符管理方式的优化**
- **`select` 和 `poll` 的问题**
  - `select` 和 `poll` 都需要在每次调用时传递一个包含所有需要监控的文件描述符的集合（`select` 使用 `fd_set`，`poll` 使用 `pollfd` 数组）。
  - 每次调用时，内核都需要遍历这个集合中的所有文件描述符，检查它们的状态。这个过程的时间复杂度是 **O(n)**，其中 n 是文件描述符的数量。当文件描述符数量较多时，这种遍历操作会消耗大量时间。
  - 此外，`select` 和 `poll` 都需要在用户态和内核态之间频繁地传递文件描述符集合，这增加了系统调用的开销。

- **`epoll` 的优化**
  - `epoll` 使用了一个独立的文件描述符集合，通过 `epoll_ctl` 将需要监控的文件描述符注册到一个 `epoll` 实例中。一旦注册完成，`epoll` 内核会维护这些文件描述符的状态。
  - 在调用 `epoll_wait` 时，内核只需要返回已经就绪的文件描述符集合，而不需要每次都重新检查所有文件描述符。这种方式避免了每次调用时的全量检查，大大减少了内核的负担。
  - `epoll` 的时间复杂度接近 **O(1)**，因为它只需要关注那些已经就绪的文件描述符，而不需要遍历所有文件描述符。

3.2 **内核态和用户态交互的优化**
- **`select` 和 `poll` 的问题**
  - 每次调用 `select` 或 `poll` 时，都需要将用户态的文件描述符集合复制到内核态，内核检查后，再将结果复制回用户态。这个过程涉及到大量的数据拷贝，尤其是在文件描述符数量较多时，数据拷贝的开销会非常大。
  - 例如，如果监控 10000 个文件描述符，每次调用 `select` 或 `poll` 都需要在用户态和内核态之间传递 10000 个文件描述符的状态信息。

- **`epoll` 的优化**
  - `epoll` 通过 `epoll_ctl` 将文件描述符注册到内核态后，内核会维护这些文件描述符的状态信息，用户态和内核态之间不需要频繁传递整个文件描述符集合。
  - `epoll_wait` 只需要返回已经就绪的文件描述符，这些文件描述符的数量通常远小于总文件描述符数量，因此数据拷贝的开销大幅减少。

3.3 **事件存储方式的优化**
- **`select` 和 `poll` 的问题**
  - `select` 和 `poll` 都是通过一个固定大小的集合（`fd_set` 或 `pollfd` 数组）来存储文件描述符的状态。这种方式在文件描述符数量较多时会浪费大量空间。
  - 例如，`fd_set` 是一个位图，每个位表示一个文件描述符的状态。如果文件描述符数量较多，位图的大小会变得非常大，而且大部分位可能都是未使用的。

- **`epoll` 的优化**
  - `epoll` 使用了动态分配的数据结构（如红黑树或哈希表）来存储文件描述符的状态信息。这种方式可以根据实际的文件描述符数量动态调整存储空间，避免了空间浪费。
  - `epoll` 的存储结构更加灵活，能够高效地管理大量文件描述符的状态。

3.4 **事件触发机制的优化**
- **`select` 和 `poll` 的问题**
  - `select` 和 `poll` 都是水平触发（Level-Triggered）机制。只要文件描述符的状态满足条件（如可读或可写），就会一直触发事件，直到应用程序将其状态清空。
  - 这种机制会导致重复触发事件，增加了应用程序的处理负担。例如，如果一个文件描述符一直可读，`select` 或 `poll` 会不断通知应用程序，即使应用程序没有及时处理。

- **`epoll` 的优化**
  - `epoll` 支持两种触发机制：水平触发（LT）和边缘触发（ET）。
  - **边缘触发（Edge-Triggered）**：只有在文件描述符的状态发生变化时才会触发事件。例如，当一个文件描述符从不可读变为可读时，才会触发事件。这种方式减少了事件的重复触发，提高了效率。
  - **水平触发（Level-Triggered）**：`epoll` 也支持水平触发，但边缘触发是其主要优势之一。

3.5 **文件描述符数量限制的优化**
- **`select` 的问题**
  - `select` 的最大文件描述符数量通常受限于系统常量 `FD_SETSIZE`，默认值通常是 1024。这意味着 `select` 最多只能监控 1024 个文件描述符，这对于高并发场景显然是不够的。

- **`epoll` 的优化**
  - `epoll` 没有固定的文件描述符数量限制，它可以通过 `epoll_ctl` 动态添加和删除文件描述符，能够轻松支持数万个甚至更多文件描述符。

3.6 总结
`epoll` 的高效性主要体现在以下几个方面：
1. 避免了每次调用时的全量检查，减少了内核的负担。
2. 减少了用户态和内核态之间的数据拷贝开销。
3. 使用动态数据结构高效管理文件描述符状态，避免空间浪费。
4. 提供边缘触发机制，减少事件的重复触发。
5. 没有固定的文件描述符数量限制，能够支持大量并发连接。

因此，在高并发场景下，`epoll` 的性能优势非常明显，能够显著提高系统的吞吐量和响应速度。

4. 既然 epoll 可以避免每次调用时的全量检查，这是怎么实现的？它是怎么知道在这些监测的文件描述符中哪些有关注的事件发生？

epoll 能够避免每次调用时的全量检查，主要是因为它采用了以下机制来高效地管理文件描述符和检测事件：
4.1 **使用红黑树（RB Tree）存储文件描述符**

epoll 内部使用红黑树来存储被监控的文件描述符及其相关信息[^1^][^2^]。当通过 `epoll_ctl` 添加、修改或删除文件描述符时，epoll 会将这些文件描述符插入到红黑树中。红黑树是一种高效的动态数据结构，能够快速地插入、删除和查找节点。

- **插入文件描述符时**：epoll 将文件描述符作为键值对插入到红黑树中，每个节点存储文件描述符及其对应的事件信息（如可读、可写等）[^1^]。
- **查找文件描述符时**：epoll 可以通过红黑树快速定位到某个文件描述符，而不需要像 select 或 poll 那样遍历整个文件描述符集合[^2^]。

4.2 **维护一个就绪事件列表（rdllist）**

epoll 内部维护了一个就绪事件列表（`rdllist`），用于存储已经准备好（即发生事件的）文件描述符[^1^]。当某个文件描述符的状态发生变化（如变为可读或可写）时，内核会将该文件描述符从红黑树中取出，并将其添加到就绪事件列表中。

- **事件检测机制**：epoll 利用内核的事件通知机制（如文件描述符的 `poll` 函数），在文件描述符状态发生变化时，内核会自动将该文件描述符加入到就绪事件列表[^1^]。
- **高效返回事件**：当调用 `epoll_wait` 时，epoll 直接从就绪事件列表中获取已经准备好事件的文件描述符，并将其返回给用户程序[^2^]。这样避免了每次调用 `epoll_wait` 时都重新遍历所有文件描述符来检查事件。

4.3 **内核事件通知机制**

epoll 通过内核的事件通知机制来检测文件描述符的状态变化[^1^][^2^]。每个文件描述符都有一个对应的等待队列（`poll_wait`），当文件描述符的状态发生变化时，内核会将该文件描述符加入到就绪事件列表中，并唤醒等待在 `epoll_wait` 上的进程[^1^]。

- **避免全量检查**：epoll 不需要像 select 或 poll 那样在每次调用时都检查所有文件描述符的状态。内核会在文件描述符状态发生变化时主动通知 epoll[^2^]，epoll 只需要维护好就绪事件列表即可。
- **高效唤醒机制**：当有事件发生时，内核会直接将进程从等待队列中唤醒，并将事件信息添加到就绪事件列表中[^1^]。

4.4 **边缘触发（ET）和水平触发（LT）模式**

epoll 支持边缘触发（ET）和水平触发（LT）两种模式[^3^]。边缘触发模式下，epoll 只在文件描述符状态发生变化时通知一次，减少了重复通知的开销。水平触发模式下，只要文件描述符的状态满足条件，epoll 就会一直通知。

- **边缘触发模式**：适用于高并发场景，可以减少事件通知的次数，提高效率[^3^]。
- **水平触发模式**：适用于对事件响应要求较高的场景，确保不会错过任何事件[^3^]。

4.5 总结

epoll 通过红黑树高效管理文件描述符、维护就绪事件列表、利用内核事件通知机制以及支持多种触发模式，避免了每次调用时的全量检查，从而实现了高效的事件检测和处理[^1^][^2^][^3^]。
